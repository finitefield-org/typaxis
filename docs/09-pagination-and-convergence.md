# Paginationと収束

通常は前方flow、page末尾の`ResourceLimits.max_page_break_lookback`以内でbreak costを比較する。keep、widow/orphan、heading isolation、table/footnote split、unused spaceをcomponent別にtraceする。lookback候補数が上限を超える入力はG6xxx errorとし、候補を黙ってtruncateしない。

`LayoutPassCoordinator`はstate-dependent resolved reference textを入力にimmutable `GeneratedTextStore` working overlay、TextPipeline、line breaking、FlowTree、fragmentationを再構築するbounded feedback loopを所有する。materialized state nは、そのpages `P_n`を実際に生成したoverlay `G_n`をpages/fingerprintと同じlifetimeで所有する。next overlayをoutput stateへ先取りしない。pass 0だけはpagination ownerがvalidated package/limitsから内部生成したunmaterialized seed `G_0`を直接使い、caller-supplied storeを受けない。pass i>0の`LayoutPassInput`はstate自体ではなく、previous materialized fingerprint `F_i`とsealed transitionが`P_i`、placed anchors、package generated-site registryから導出したworking `G_{i+1}`を組にする。pass iは`P_{i+1} + G_{i+1}`をmaterializeする。したがってnext pass input fingerprintは直前output `F_i`と一致しつつ、working overlay/reference epochはtransition結果へ変化できる。Paginatorはpage planを選ぶだけでshapeしない。

`PaginationWorkBudget`は全passで変わらないDocument/Style/AdmittedResourceのbase identityを固定し、ReferenceFingerprintはpassごとのworking `LayoutEpoch`としてpermit/receiptへ記録する。full LayoutEpochをbudget作成時の値へ固定しない。`PaginationInput`はさらに非シリアライズのopaque `PaginationSessionId`を1件発行し、budget、pass materialization receipt、`LayoutPass`、`ReferenceTransitionReceipt`、次の`LayoutPassInput`へ同じcapabilityを伝播する。capabilityはallocation-localなpointer identityであり、`Debug`はopaque、global counterやexhaustion stateを持たない。in-process trusted receiptの等価性はsession-scopedとし、canonical stateの等価性はfingerprintだけで判定する。`begin_pass`はworkを減算する前にsession、expected state index、stable base identity、working reference/store identityを照合するため、別sessionが同じcanonical output fingerprintを持っていてもそのtransition receiptを流用できない。このsession capabilityはJCS、trace、manifest、fingerprintの入力に含めない。transition receiptのprevious fingerprint/pages/anchors/site-registry bindとworking store/epoch bindが一致しなければpassを開始しない。reference workspaceの`InitialPaginationState`はpackage-issued canonical marker/empty-site overlayを使い、次passはexact predecessorのplaced anchorsからpage-reference bytesを更新したowned overlayを発行する。別storeをcallerが注入する経路はない。

`PaginationInput`は`ValidatedResourceLimits`からsingle-issueの`PaginationWorkBudget`を発行し、各`FragmentRequest`はそのbudgetを`FragmentWorkBudget`として共有する。line reshapeは別の`LineLayoutBudget`を同じlimitsから発行する。page、fragment、lookback、line reshape、footnote reflow、column candidate、float queue/carryはそれぞれmax+1回目のwork/enqueue/allocation前にconsumeし、完成済みVecの長さを後から検査するだけで上限を証明しない。external Paginator/Fragmenter implementationにもこの全budget receiptを渡し、一部counterの脱落を型で禁止する。

flowが空でもmaterialized page sequenceを空にしない。default masterを使うpage index 0のblank pageをちょうど1枚生成し、fragment、annotation、destinationを空にする。このblank pageも通常のstate fingerprint、Display構築、PDF page tree、page/output limitへ含める。

state 0のwireはpagesを持たない専用`InitialPaginationStateRecord { algorithm = typaxis.initial-pagination-state/1, flow_positions, layout_epoch, resolved_generated_text }`である。各materialized stateは`PaginationFingerprintRecord { algorithm = typaxis.pagination-fingerprint/1, flow_positions, layout_epoch, pages, placed_anchors, resolved_generated_text }`を完全に持つ。`flow_positions`は当該stateのcanonical FlowTree boundary registryである。nonblank flowはindex 0にDocument rootの`DocumentStart (ordinal=0, owner=0, path=[], local_boundary=0)`、index 1..len-2にboundary tuple `(owner, block_child_path, owner_local_boundary)`順かつ同じ`(owner,path)`内local 0-based denseのpaintable boundaries、last indexにrootの明示的な`End (owner=0, path=[], local_boundary=1)`を持つ。`global_flow_ordinal`は常にarray indexと一致するが、先頭DocumentStartと末尾Endは中間tuple sortの対象外である。blank flowだけはsole DocumentStartがterminalを兼ねる。fragment start/endはregistry recordのexact memberでなければならない。`placed_anchors`は選択page/frameへ結合された`(anchor_id, owner_node, page_index, frame_kind, column_index, position_in_frame)`の完全な集合で、AnchorId UTF-8 byte順にする。state 0を任意fingerprint文字列やblank page recordで偽装しない。

state 0はunmaterializedなので、blank documentでもpass 0 outputのblank page stateとは一致しない。pass 0が`P_1 + G_0`をstate 1としてmaterializeする。site 0件ではunchanged transitionが同じworking overlayを発行し、pass 1が同じ`P_2 + G_1`を出してstableになる最短2-pass収束である。

- stable: current input == current output
- cycle: current outputが以前のmaterialized state 1..iのfingerprintに現れ、current inputとは異なる。domain-separatedなunmaterialized seed state 0は比較対象にしない
- max-pass: stable/cycle前に`max_layout_passes`へ到達

`PaginationFingerprintEncoder`だけが専用`PaginationFingerprintRecord`を構築する。recordはpageをdense `page_index`順、各pageのframeを`body < header < footer < footnote`とcolumn index順、fragmentを`(start FlowPosition, owner NodeId, owner-local ordinal)`順、footnote assignmentをFootnoteId UTF-8 byte順、float decisionを`(owner NodeId, owner-local ordinal)`順、column decisionを`(container NodeId, column index)`順、placed anchorをAnchorId UTF-8 byte順、resolved reference textを`GeneratedBufferKey`順のarrayで持つ。各sort keyは一意でなければならず、duplicate/gap/unknown ownerをencoderが拒否する。unordered mapを直接encodeしない。

fingerprint対象はpage master、frame、fragment owner/ordinal/start/end/bounds、footnote assignment、float decision、column decision、placed anchorのID/owner/page/frame/column/local point、resolved reference textのprovenanceと正確なUTF-8 bytesを含む。したがってanchor集合または座標だけが変わるpassをstableとして扱わない。state index、pass index、diagnostic、trace metadata、allocation IDは除外する。上記canonical recordをRFC 8785 JCSでencodeしてSHA-256を計算し、JCSにarray順の正規化を期待しない。Node-to-pageだけのfingerprintやopaque progress tokenで代用しない。

各pageは選択master、page index、frame bounds、page直下のfragments、footnote IDs、float/column decisions、resolved referencesを持つ。fragmentとfloat decisionは`frame_kind,column_index`で既知frameを参照し、boundsがそのframe内に収まる。frame kindは選択masterのbody/header/footer/footnote regionに対応し、null regionを参照しない。fragment endはstart owner境界を跨いでよいが、start ownerはfragment ownerと一致する。

stable時はstableなmaterialized stateを選ぶ。cycle/max-pass時の候補は実際にpageをmaterializeしたstate 1..pass_countだけで、state 0は含めない。各stateはcanonical `fallback_score = (hard_violation_count, total_cost, page_count, state_index)`を持つ。hard violation count、page count、state indexはnonnegative JSON-safe checked integer、各penalty componentとそのchecked sumであるtotal costはsigned JSON-safe integerとし、overflowはG6xxx errorにする。このtupleの辞書式最小を選び、profile 1.0のpolicy IDは`lowest_cost_then_earliest`で固定する。fallback選択はG6xxx warningを必ず出し、`--strict`では同codeをerrorへ昇格してPDFを生成しない。strictでないbuildは選択stateからPDFを生成できる。traceはtermination reason、全候補score、selected stateを記録し、build manifestの`layout`はstatus、pass count、selected state、final fingerprint、fallback policyだけを記録する。silent convergenceを禁止する。
