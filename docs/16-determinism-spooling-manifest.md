# Determinism、spooling、build manifest

再現性入力はsource bytes、effective config、font/image bytes、Unicode/Japanese table version、shaper backend/version、engine version、PDF profile、configの`pdf_stream_compression` mode。ConfigLoader/CLIが`built-in defaults < typaxis.toml < TYPAXIS_ environment < canonical CLI override`の順に解決する。raw `typaxis.toml`はexact `contract`を必須とするpartial typed overrideで、unknown keyを拒否する。merge後は全fieldを持つ`package-config.schema.json`のcanonical `EffectiveConfig`としてpositivityとcross-field relationまで検証する。

version stringを事実としてcallerから受け取らない。configの`data_versions`はengineに登録済みのimmutable Unicode/Japanese table setを選ぶselectorであり、unknown pairをconfig errorにする。解決済みtable handleが所有するversionだけを`EffectiveConfig`とmanifestへ投影する。shaper backend/versionはarbitrary stringを受けず、closed `ShaperIdentity`が表すlinked registry selectionをmanifestへ投影する。このidentity fact単独はactual shaping invocationのcapability proofではなく、reference workspaceのmanifestもそれを主張しない。完成runtimeがactual-useを保証する場合は実shaper sessionが発行しlayout/publication artifact chainまで保持するsealed receiptを追加する。engine name/version/Rust version/git commitはbuild metadataから作るopaque `EngineIdentity`だけを受け、公開manifest fieldをcallerが個別設定しない。Profile 1.0の登録値はUnicode `16.0.0`、Japanese `typaxis-jlreq-horizontal/1.0.0`、shaper `typaxis-reference-shaper/0.1.0`である。

`TYPAXIS_` environment keyはtop-level fieldをupper snake case、nested fieldを`__`で結ぶ（例: `TYPAXIS_STRICT`、`TYPAXIS_LIMITS__MAX_INPUT_BYTES`）。値はそのfieldの単一TOML valueとしてUTF-8 parseし、unknown key、invalid UTF-8、type/range errorをP1xxx config errorにする。canonical CLI overrideは`--strict`、`--no-compress`、`--max-<limit>`などPDF意味論を変えるtyped optionだけである。`--config`、host `--resource-root`、output/sidecar path、`--force`、trace表示optionは`EffectiveConfig`へ入れない。

`HostAdmissionContext`はentry/project/config pathと明示されたhost resource rootsを持つが、host absolute path自体はJCS hashやmanifestへ入れない。host root順はcandidate検査とdiagnosticだけを安定化し、最初に存在したfileを選ぶprecedenceではない。`typaxis.toml`の`resource_roots`は`ConfigResourceRoot`のcanonical arrayとしてeffective config/hash対象になる。wire `"."`は`ProjectRoot` variantであり、relative variantだけが`PortablePath`を持つ。set意味の`resource_roots`と`allowed_uri_schemes`はduplicateを拒否し、wire stringのUTF-8 byte昇順にsortしたcanonical arrayだけをEffectiveConfigに許す。同じsetを別順序で記述してもmerge/validation後のJCS bytesは同一になる。manifest builderは解決をやり直さず、受け取ったeffective configをcontract-defined JSON valueへ変換し、RFC 8785 JCS UTF-8 bytesのSHA-256を`config_sha256`として記録する。raw TOML bytesだけをeffective config hashとして使わない。

canonical JSON artifactとfingerprint inputはRFC 8785 JCSでencodeする。build manifestの`inputs`はunique `PortablePath`のUTF-8 byte順、`fonts`はunique `font_face_id`数値順、`images`はunique `image_id`数値順にする。manifestの`layout`はstatus、pass count、selected state、final fingerprint、fallback policyを記録し、fallback score詳細はtraceだけに置く。manifestの`stream_compression`はeffective configの`pdf_stream_compression` modeと一致しなければならない。spoolはpage recordごとにmagic、contract、length、checksumを持つ。最大page/total bytesを割当前に検査し、temp root外を削除しない。異常終了時のcleanupは作成したnonce directoryだけ。

repositoryのpretty JSONはreview用のhuman-readable data-model fixtureであり、そのindent/member順をcanonical wire bytesとは主張しない。`samples/minimal/jcs-golden.json`が各minimal artifactとeffective configのcanonical RFC 8785 JCS bytesをbase64とSHA-256で固定し、validatorがdecode後のbytesを再計算値とexact比較する。全JSON stringはUnicode scalar sequenceだけを許し、unpaired surrogateを共通semantic gateで拒否する。

manifestのactual admitted metadataはfont `units_per_em`をProfile 1.0 TrueType有効範囲16..16384、`glyph_count`とimage `pixel_width/pixel_height`を1..4294967295に狭め、Rust admissionが発行できる値域と一致させる。exact min/maxは受理し、min-1/max+1をwireで受理しない。

canonical build manifestのstatusはterminalな`built`または`failed`だけで、公開`planned` stateを持たない。CLI parseとcanonical `EffectiveConfig`検証後は、manifest optionの有無にかかわらず`BuildExecutionContext`からper-build `BuildOutputCommitContext`を構築する。`--emit-build-manifest`でtargetが指定された場合だけ、同じoutput contextへbindした`ManifestPublicationContext`を追加構築する。それ以後のsource/resource validation、layout、PDF生成失敗ではcleanup後に`status = failed`、`output = null`をatomic publishする。manifest context成立前のconfig/usage failureは必須config factsを捏造せず、manifestを変更しない。failed recordの`inputs`/`fonts`/`images`は失敗境界までに検証・admit済みのrecordだけをcanonical順で含み、完全な集合とは主張しない。materialized/selected layoutが確定済みなら`layout` summaryを含め、未確定なら`layout = null`にする。

manifestのFile/Font/Image/Layout/Output recordと`BuildManifest`本体はpublic field constructorを持たない。各`BuildOutputCommitContext`と`ManifestPublicationContext`はそれぞれopaqueなper-build session identityを持ち、同じconfig、target、engine factsで別に作ったcontext間でもPDF receipt、ledger、preflight tokenを混用できない。context collateralの`ManifestAdmissionLedger`だけが`SourceRecord`、`ValidatedParsedPackage`、`AdmittedResourceLedgerToken`から失敗境界までのfactsを複写でき、failed factoryはこのledgerとoptional coherent `PaginationResult`だけを受ける。layout summaryを付ける場合はvalidated package epochとadmitted resource fingerprintの両方をledgerへ収容済みにし、partial ledgerでは`layout = null`だけを許す。

built publicationは`ValidatedParsedPackage + AdmittedResourceLedgerToken + selected PaginationResult + VerifiedPdfBytesReceipt`をI/O前にpreflightし、source/resourceの完全集合、document/style/resource epoch、selected fingerprint/page/object/bytes/hash、EffectiveConfig fingerprint、compression mode、全limitsを再照合し、canonical manifest bytesもI/O前に確定する。この検査にすべて成功した`PreparedBuiltPublication`だけを、それにbindしたnon-cloneable `BuildOutputCommitContext`がself-consuming commitでexact configured sinkへ送れ、token内のtrusted manifestはcommit前に公開しない。PDFとmanifestの両durable commit成功時はvalidated manifest、`PdfSinkCommitReceipt`、`ManifestSinkCommitReceipt`を同時に返し、PDFを書いた後に失敗し得るbuilt validation/serializationを残さない。atomic publish後のdirectory syncだけが失敗した場合はtargetが既にvisibleなので、専用durability-uncertain errorが該当receiptまたはcomplete publicationを所有し、uncommitted/rollbackとして扱わせない。manifest targetが無いbuildでは同じoutput contextがnon-cloneable serializer-issued `VerifiedPdfBytesReceipt`のconfig fingerprint/compression/page/object/bytes limitsをpreflightしてPDFだけをcommitする。manifest targetが有るcontextはこの単独経路を拒否し、sealed built preflightを迂回できない。別output sessionのtoken、cloneしたcontext/receipt、caller-authored record、任意callbackのsuccessはtrusted publicationにならない。failed manifestもsession-bound `PreparedFailedPublication`を経てatomic sidecar commit後だけtrusted record/receiptを公開する。

`status = built`は完全なlayoutとoutput factsを必須とし、`output.page_count >= 1`にする。empty documentもdefault-master blank pageを1件数える。output recordはhost path/URIを持たず、`sink = file | stdout`だけを記録する。sealed terminal committerはfile/stdout PDFのcomplete commit後にmanifest targetと同directoryのtempへcanonical bytesを書いてfsyncし、replace policyに対応するatomic primitiveでpublishしてdirectoryもsyncする。manifestのtemp write/fsyncまたはatomic primitiveがpublish前に失敗した場合は既存manifestを変更せず、errorが既に発行済みのPDF sink receiptを保持してPDFだけがcommit済みであることを明示する。rename/hard-link後のdirectory sync失敗では新manifestは既にvisibleなのでcomplete publicationとsync errorを返す。どちらもPDFやmanifestをrollbackしたと偽らない。

PDF serializerは`FrozenPdfGraph`のactual bytes/hash/page/object count/selected fingerprint、実際のstream compression mode、serializationに用いたEffectiveConfig fingerprintへbindした`VerifiedPdfBytesReceipt`を発行する。configured `BuildExecutionContext`とper-build sessionを所有するsealed `BuildOutputCommitContext`だけが、manifest無しならそのreceipt、manifest有りならpublication preflight tokenを消費し、exact config/artifact chainを照合してからfile atomic commitまたはstdout complete writeの成功後に`PdfSinkCommitReceipt`を発行できる。任意callbackの`Ok`、arbitrary byte slice、caller-supplied hash/countだけでcommit receiptを作らない。

CLI tokenが正確に`OUTPUT = "-"`なら`BuildExecutionContext`の`OutputSink::Stdout`とし、build manifestは`output.sink = "stdout"`を記録する。その他のHostPath（`./-`というfile名を含む）は`OutputSink::File`で、manifestは`output.sink = "file"`を記録する。どちらもhost pathをserializeしない。bytes、SHA-256、page count、object countはstreaming中にchecked集計し、stdoutへの全PDF bytes writeが成功した場合だけ`status = built`とoutput factsをpublishできる。stdout write失敗時は`status = failed`、`output = null`とし、部分streamをbuilt outputとして記録しない。stdout成功後のmanifest publish失敗は、既に送信済みのPDF bytesを取り消せないI/O failureである。

file PDF outputはplatform-registered committerがtargetと同じdirectoryのtemp fileへwrite/fsyncし、`--force` policyに応じたatomic replace/no-replace primitiveでcommitする。sink ownerは各writeの直前にoutput/trace/manifest全targetを現在のcanonical pathと利用可能なfile identityから再解決し、構築後にsymlink/hard-link aliasへ変化していれば一切writeせずfail closedにする。既存outputを失敗途中でtruncateしない。reference Rust workspaceが実装するfile committerはUnixのsame-directory rename（replace）とhard-link publication（no-replace）だけであり、非Unix platformまたはatomic primitiveを提供しないfilesystemではfail-closedのI/O errorとしてreceiptを発行しない。no-replaceのtarget link成立後はtemporary-name cleanup失敗をrollback errorへ変換せずbest effort cleanupとし、その後のdirectory sync失敗はreceipt付きdurability-uncertain結果にする。完成CLIは対象platformの同等primitiveをsealed committer内に登録する。stdout出力ではdiagnosticをstderrに分離する。

release ZIPのtop-level directory名はcheckout directoryのbasenameから導出せず、版付きの`ARCHIVE_ROOT`定数で固定する。同じpackage bytesは展開元のdirectory名に関係なく同一ZIPになる。
